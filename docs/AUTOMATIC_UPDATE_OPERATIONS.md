# 非AI更新の運用と残る開始空白（2026-10-28）

- 日常の期限判定・対象選択・通信間隔・取得・保存・集計・検証・Git公開は既存Priority／Daily／Safe／Watchで実行する。Codexやチャット再開を起動条件にしない。取得済み原票は既存artifact回収を優先し、仕様・認証・許諾・403は自動解除しない。
- 通常データ更新は価格・仕様・日時・版整合の必須検証。コード／回帰テスト／workflow／アクセス方針が変更された初回は関連回帰を実行して、その指紋を保存する。週次全体試験は別に継続。同じ入力だからと実際の新しい確認日時を捨てない。
- Priorityの共通間隔ゲートで取得スキップした回は、新しい取得受領証・データコミット・Pagesを作らない。Watchの既存reuseも再取得・全件再測定・再公開を行わない。監視の新しい鮮度・障害観測は実績として保存する。
- 公開照合は既存Watch内の独立した読取専用ジョブで行う。取得排他・補完の終了待ちを使わず、公開受領証、実行の取得／検証／保存工程、Pages、公開ファイルのハッシュを照合する。4分を超えた公開待ちは失敗証跡を残し、次の通常実行で再確認。401／403や仕様不正は連続再試行しない。照合証跡だけのためにPagesを再発行しない。
- 過去に確認できた実行と、現在の公開データとの一致は別。後の価格更新・取得なし監視で過去の定期成功を取消さず、直近照合と過去証跡を保存する。

## GitHub外の開始保証が必要な場合

Priorityの2026-10-28 01:27:17→08:42:13Zは作成間隔7時間14分56秒。Watchのscheduleも00:44→06:19Zの空白があり、同じGitHub cronだけで定刻を保証できない。途中の05:41 workflow_run補完は269枚を実確認・公開したが、開始空白自体の解消ではない。GitHubの[公式説明](https://docs.github.com/en/actions/how-tos/troubleshoot-workflows)も高負荷時の遅延・ジョブ欠落の可能性を示す。今回の個別空白の内部原因はAPIから断定しない。

代替案はGitHub外の非AIタイマーが鮮度を確認し、必要な時だけ既存Priorityのworkflow_dispatchを呼ぶこと。未実行回数分は繰り返さず、既存の間隔・対象・排他制御をそのまま使う。例としてCloudflare Workersの毎時1回（24回/日）は[Freeの100,000リクエスト/日・Cron5個の枠](https://developers.cloudflare.com/workers/platform/limits/)内を想定できるが、実際の利用量・制限を確認してから判断する。有料プランは不要な案として準備し、無料枠でも登録・導入は未実施。

必要な承認・操作：利用サービスのアカウント、対象リポジトリだけの[Actions write権限](https://docs.github.com/en/rest/actions/workflows#create-a-workflow-dispatch-event)、新しい秘密情報の保管先。既存認証情報を勝手にクラウドへ移さない。導入・登録・課金・問い合わせは今回行わない。workflow_dispatchでもGitHubのランナー待ちは残るため、6時間維持の保証とはしない。
