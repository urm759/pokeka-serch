# ポケカ仕入れ判断サイト

この `github-site` フォルダだけで、GitHub Pages の表示とデータ自動更新が動きます。

## GitHub にアップロードするもの

- アップロードするのは、この `github-site` フォルダの中身だけです
- `index.html` が GitHub リポジトリのルートに見える配置にします
- 親フォルダ側の `work`、`.github`、`outputs` を別々にアップロードする必要はありません
- `.github/workflows/refresh-all-site-data.yml` で毎日04:30と17:00（日本時間）に全データを一括更新します
- 個別の相場更新とカードラッシュ更新は、Actions画面から手動実行できます

## 仕組み

- `index.html` が本体
- `app.js` でフィルタと利益率計算
- `data/pokemon-cards-meta.json` にデータ取得日を保持
- `data/pokemon-cards.json` に `toreca-souba.com` のポケモンカード全件を集約
- 画面上で `PSA鑑定費`、`直近30日下限`、`直近7日下限`、`利益率下限`、`PSA10上下限`、`平均美品価格帯`、`検索` を変更可能
- URL パラメータ `?fee=13000&tx=30&tx7=0&roi=40&psaMin=0&psaMax=200000&priceMin=&priceMax=&sort=roi-desc&q=` にも対応
- 平均美品価格は、みんトレ・カードラッシュ・晴れる屋2の状態A価格から異常値を除外した中央値。1店舗だけ市場価格から大きく離れる場合は計算から除外し、画面に「異常値・要確認」と表示
- 利率は `利益額 ÷ (平均美品価格 + PSA鑑定費) × 100`
- 美品の動きは、みんトレ取引件数とカードラッシュで確認できた在庫減少数を7日・30日で分けて表示

## 変更しやすい箇所

- PSA鑑定費を変えたい: 画面上部の入力欄
- 取引数の条件を変えたい: `直近30日 下限`
- 直近7日の動きも絞りたい: `直近7日 下限`
- PSA10 20万円以下に絞りたい: `PSA10 上限`
- PSA10 の最低価格も見たい: `PSA10 下限`
- 美品の値段レンジを絞りたい: `美品 価格帯`
- データ取得日を変えたい: `data/pokemon-cards-meta.json`
- 画像やカードを増やしたい: `data/pokemon-cards.json`
- 並び順を変えたい: `並び順` セレクト

## 自動更新

`Refresh All Site Data` が毎日2回、日本時間の午前4時30分と午後5時に開始します。
みんなのトレカ相場の新カード・価格・取引件数を取得したあと、スニダン直リンク、カードラッシュの商品・状態A価格・在庫を順番に更新します。
午前4時30分開始分は、通常は午前6時までの完了を見込んだ設定です。ただしGitHub Actions側の混雑や取得元サイトの応答状況によって遅れることがあります。

更新の最後に `work/build_evaluation_model.js` が同じPSA10価格帯の取引・買取掲載・利益率の分布を再集計します。画面の「銘柄品質」は売りやすさ35%、価格安定25%、供給リスク耐性15%、将来価格25%です。購入価格に左右される利益条件は混ぜず、「今回の仕入れ判断」で別に評価します。

`Refresh Pokemon Site Data` と `Refresh Cardrush Stock` は個別確認用の手動実行として残しています。通常の定期更新は `Refresh All Site Data` だけで完結します。

### 手動で今すぐ一斉更新する

スマホまたはPCで GitHub のリポジトリを開き、`Actions` → `Refresh All Site Data` → `Run workflow` → 緑色の `Run workflow` の順に押します。処理と公開はGitHub側で行うため、自分のPCを起動したままにする必要はありません。

みんトレ、カードラッシュ、Web買取表、トレカクラブ、PSA Japan料金、評価モデルはこの操作で更新できます。PSA公式PopulationはCloudflareのログイン確認があるため、ログイン済みChromeを使った手動補完が必要です。Xの画像買取表も新着検出までは自動ですが、誤照合防止の最終確認だけ手動です。

## お気に入り仕入れ候補

各カードの「仕入れ候補に追加」からお気に入り登録できます。登録内容はブラウザごとの保存ですが、CSV保存とCSV読込で別のスマホ・PCへ移せます。
メモ用コピーでは、カード名、PSA10価格、美品と多少の傷ありの仕入れ上限をスマホで確認しやすい形式にまとめます。

## 状態別の仕入れ上限

各カードの上部に「美品なら」「多少の傷ありなら」の2つの仕入れ上限を表示します。美品はPSA公式取得率、公式未取得時は選択中の70%または50%基準を使用します。多少の傷ありは美品のPSA10取得率を45%下げ、PSA9以下の回収額も安全側へ補正して再計算します。仕入れ上限と現在価格での期待利益は `decision-model.js` の同じ前提・計算式を使います。

PSA9市場価格があるカードは実価格、未取得時は平均美品価格の75%をPSA9以下の参考額にします。91日後のPSA10中央推計、鑑定費、売却手数料、最低期待利益・利益率・年換算効率に加え、予測下落余地、回転、売りやすさ、価格安定性、データ充足度を安全余裕として反映し、500円単位で切り下げます。

## PSA提出判断

`PSA提出判断の設定` で、仕入れ用総資金、ロック中資金、資金ロック日数、最低期待利益、最低期待利益率、最低年換算資金効率、1枚の最大資金占有率、同時提出枚数、返却時の鑑定費予備資金、売却手数料、送料等を変更できます。
入力値はURLへ自動反映されるため、そのURLをブックマークすると同じ条件で再度開けます。

使用可能資金は `総資金－ロック中資金－鑑定費予備資金` です。カードごとの仕入れ上限は利益条件で算出し、同時提出予定枚数で割った1枚あたり資金枠は別に表示します。現在価格×同時提出枚数が使用可能資金を超える場合はGOにしません。鑑定費予備資金が `1枚の鑑定費×同時提出枚数` を下回る場合も見送りです。

期待利益は `PSA10率×PSA10手取り＋（1－PSA10率）×PSA9以下手取り－仕入れ価格－鑑定費` を基本に、予測下落・回転・データ不足の安全余裕を差し引きます。PSA10率は公式値、PSA9は実価格を優先し、未取得時だけ画面設定と平均美品75%を使います。売却手数料と送料等はPSA10・PSA9以下の両方から差し引きます。

最終結論は「GO／価格次第／見送り」です。期待利益がマイナスのカードは必ず見送りになり、銘柄品質が良くても仕入れ候補扱いにはしません。価格の異常値があるカードは自動GOにせず、確認が必要な「価格次第」とします。

## 91日後の価格推計

PSA10の将来価格は期間を91日後と明示し、弱気・中央・強気の3価格を表示します。「データ充足度」は取引件数、買取店舗、PSA公式取得率・増加履歴、ショップ紐付けの取得状況を表し、価格上昇を保証する確度ではありません。買取価格は最新日の有効価格の中央値を予測へ使い、市場PSA10価格から大きく離れた単独店舗値は除外します。

## 計算テスト

`node work/test_decision_calculations.js` で、資金計算、公式PSA10率とPSA9実価格を使う期待利益、中央値と異常値除外、GO／見送りを同じ共通計算モジュールに対して検証します。

## PSA公式Population履歴

厳格照合できたカードだけ、PSA公式のPSA10枚数、TOTAL枚数、PSA10取得率を表示します。7日・30日・90日のPSA10増加を「急増化・増加・少ない・横ばい」で評価します。
履歴は32分割したJSONへ数値だけを保存し、カードの「推移を見る」を開いた時だけ該当ファイルを読み込み、SVGグラフをブラウザで描画します。

PSA公式ページはログインが必要なため、Windowsのログイン済み専用Chromeから午前4時30分、午後5時、Windowsログオン時に取得を試します。同日に1回成功した後は重複実行しません。
最初に `node work/open_psa_login.js` でPSA専用Chromeへログインし、`powershell -ExecutionPolicy Bypass -File work/install_psa_tasks.ps1` で定期タスクを登録します。

- `work/update_pokemon_site.js` を実行すると、toreca-souba の公開データからポケモンカード一覧とメタ情報を再生成します
- `work/update_snkr_links.js` が未取得の全カードを確認し、スニダン個別商品URLを100枚ごとに保存します
- `work/update_cardrush_links.js` が2015年以降のカードラッシュ状態A商品を増分取得し、目標カバー率90%まで進捗を保存します
- カードラッシュは状態Aまたは状態表記なしだけを直リンクに採用し、状態A-・B・C・Dは除外します
- `work/update_cardrush_stock.js` が状態A価格と在庫を日次保存し、7日・30日・90日の平均減少数と需要判定を生成します
- 在庫履歴は直近91日だけ保持するため、毎日蓄積しても容量が増え続けません
- 商品URLを2日続けて確認できない場合は無効候補として再検索キューへ入れます
- マスターボールミラー、モンスターボールミラー、通常ミラーなどは、商品名の特殊仕様が一致する場合だけ紐付けます
- GitHub Pages用には、画面で使う最小項目だけを圧縮したJSONを書き出します
- 2つのワークフローは定期実行と手動実行の両方に対応しています
- GitHub Actions上で実行するため、更新時に自分のパソコンを起動しておく必要はありません
- GitHub Pages では、ワークフローが更新した `data/*` をそのまま配信します

## GitHub Pages に置く方法

1. この `github-site` フォルダを開く
2. 中にあるファイルとフォルダをすべて GitHub リポジトリのルートへアップロードする
3. GitHub Pages の公開元を `Deploy from a branch`、ブランチを `main`、フォルダを `/(root)` に設定する
4. Actions の `Refresh Pokemon Site Data` と `Refresh Cardrush Stock` を有効にする

## 現在の抽出条件

- ポケモンカードのみ
- 直近30日の取引数が 30 件以上
- 利益率が 40%以上
- PSA鑑定費は初期値 13,000円

## 現在の直リンク状況

- スニダン: 全カードに個別商品リンクを保存
- カードラッシュの最新件数は、サイト上部の「カードラッシュ」集計に表示
- 鑑定済み商品と状態A-・B・C・Dへのリンクは含みません

## X買取表の画像解析

`work/analyze_x_buyback_sheet.py` は、買取表画像ごとに行数・列数・カード枠・価格欄を再検出します。店舗ごとの固定座標には依存しないため、配置が変わった場合も新しい構造として解析し、信頼度が基準未満なら自動登録しません。

```powershell
python work/analyze_x_buyback_sheet.py INPUT_IMAGE OUTPUT_DIR
```

出力先には、検出結果の `manifest.json`、カードと価格の切り出し画像、確認用の `contact-sheet.jpg` が作られます。現在のローリエ本舗AKIHABARAの検証画像11枚では、配置と価格を338件中338件正しく検出しています。

カード名は画像だけで無理に確定せず、確認済みの `verifiedCardId` がある行だけ掲載数へ登録します。現在確認した338件は322件を登録し、元データの対応カードを確定できない16件は保留しています。確認済み範囲の紐付け率は95.3%で、登録済みカードの誤登録は0件です。検証値は `work/x_buyback_analyzer_metrics.json` に保存します。

XはGitHub Actionsからログイン済みChromeを利用できません。投稿画像の取得とカード名の最終確認はログイン済みChromeで行い、取得後の表分割・価格読取・重複排除・履歴集計をこの仕組みで処理します。画像本体はリポジトリへ保存しないため、GitHub Pagesの容量は増えません。
